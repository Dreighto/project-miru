## Recommendation: Hybrid (W4 dispatch-time + n8n bridge at completion-time)

Split the work across two independent components:

**Component 1 — W4 dispatch workflow modification:** Todo → In Progress state move at dispatch time. Covers all four workers universally (worker-agnostic). Three new nodes appended to the existing W4 success chain after `w4027-update-pending-dispatched`.

**Component 2 — New n8n bridge workflow:** Watches `cc_completion_log.jsonl`, posts findings comment + moves In Progress → In Review on completion (CONFIRMED_WORKING only). Covers CC workers in v1; extensible as other workers adopt the completion contract.

### Why hybrid wins over pure A, B, or C

| Criterion                    | A (listener)         | B (worker) | C (n8n bridge)       | Hybrid          |
| ---------------------------- | -------------------- | ---------- | -------------------- | --------------- |
| Knows issue_id at dispatch   | No (not in payload)  | No         | N/A                  | Yes (W4 has it) |
| Knows findings at completion | No (receipt is thin) | Yes        | Yes (completion log) | Yes             |
| Workers changed              | 0                    | All 4      | 0                    | 0               |
| Listener changes             | Yes                  | 0          | 0                    | 0               |
| Reuses proven patterns       | No                   | No         | Yes (PRO-160)        | Yes             |
| Blast radius if broken       | All dispatches       | Per-worker | Only Linear writes   | Split           |

**Option A fails** because the listener doesn't know `issue_id` (dispatch payload is `{trace_id, worker, prompt_path, timeout_seconds}` only) and has no structured findings (receipts have `summary: ""`, `files_touched: []`).

**Option B fails** because it couples every worker binary to the Linear API. Only CC currently writes completion markers. Requiring 4 worker changes is impractical.

**Pure C fails** because the Todo → In Progress move must happen at dispatch time (before the worker starts), and the completion log is only written at task end.

## Component 2: n8n Bridge Workflow (Findings → Linear)

### Architecture

New workflow `w-linear-completion-bridge.json` using the proven PRO-99/PRO-160 pattern:

```
wlcb001-schedule-trigger (60s)
  → wlcb002-read-and-diff (SHA-1 hash-set diff, separate static-data keys)
    → wlcb003-regressed-branch
      → [regression]: wlcb003a-build-msg → wlcb003b-send-telegram
      → [normal]: wlcb004-split-rows
        → wlcb005-parse-row (extract fields, build comment with hash marker)
          → wlcb006-skip-branch
            → [skip]: wlcb-noop-skipped
            → [process]: wlcb007-lookup-issue (Linear GraphQL: issue + states)
              → wlcb008-resolve-ids (extract issue UUID + In Review state ID)
                → wlcb009-post-comment (Linear commentCreate, retry independent)
                  → wlcb010-move-in-review (Linear issueUpdate, only on CONFIRMED_WORKING)
```

### Hash-set diff

Identical algorithm to `ccp002-read-and-diff` but with separate static data keys:

- `lc_pinged_hashes` (array of SHA-1 hex strings)
- `lc_regression_alerted` (boolean)

Two independent watchers on the same append-only file is safe — like two Kafka consumer groups. Each has its own n8n workflow static data namespace (isolated by workflow ID). No shared mutable state.

### Comment format

```markdown
✅ **CC CONFIRMED_WORKING**

Fixed heartbeat schema to include step field

**Test evidence:** 15/15 fixtures pass
**Branch:** `dreighto/pro-180-heartbeat`
**PR:** #42
**Merge SHA:** `a1b2c3d`

**Files touched:**

- `tests/test_x.py`
- `tools/emit_heartbeat.py`

<!-- bridge:hash:abc123def456 -->
```

The `<!-- bridge:hash:... -->` HTML comment marker enables future dedup queries (invisible in Linear UI, queryable via `issue.comments`).

### State transitions at completion

| Completion status | Linear state move             | Comment posted? |
| ----------------- | ----------------------------- | --------------- |
| CONFIRMED_WORKING | In Progress → In Review       | Yes             |
| INCONCLUSIVE      | No change (stays In Progress) | Yes             |
| FAILED            | No change (stays In Progress) | Yes             |

The state move logic in `wlcb010-move-in-review` checks `status === 'CONFIRMED_WORKING'` AND the issue lookup succeeded AND the In Review state ID was resolved. Otherwise sends a harmless `query{__typename}`.

### Error workflow

`l5wzFuWnJ2zSoMM2` (W1 error handler). Bridge crashes file a Linear ticket automatically.

## State Machine (full lifecycle)

```
           [Todo]
              │
              ▼  W4 dispatch succeeds (202)
        [In Progress]
              │
     ┌────────┼────────┐
     │        │        │
     ▼        ▼        ▼
[In Review] [stays    [stays
             In Prog]  In Prog]
  (CONFIRMED  (INCON-   (FAILED
   _WORKING)  CLUSIVE)  + comment)
     │
     ▼  operator manual
   [Done]
```

### Edge cases

**Timeout (600s):** Listener kills worker, writes FAILED receipt + DLQ. If worker wrote completion row before kill → bridge fires. If not → ticket stays In Progress → stall watchdog (PRO-100) catches eventually.

**Listener crash mid-spawn:** Orphan sweep marks receipt FAILED. No completion row → ticket stays In Progress. Same stall-detection gap.

**W4 crash between 202 and state move:** Worker runs normally. Bridge eventually moves ticket to In Review (skipping the In Progress step). Acceptable — In Review is a superset. Bridge does NOT assert "must be In Progress first."

**n8n container restart:** Both watchers resume from persisted static data. Rows that arrived during downtime are detected as new (hash not in set) and processed.

## Idempotency

### State moves

Linear's `issueUpdate` is idempotent — setting `stateId` to the current state returns `success: true` with no side effects.

### Comment deduplication (v1: marker-only)

The `<!-- bridge:hash:<row_hash> -->` HTML comment is included in every bridge-posted comment. The marker enables a future dedup query (skip post if marker already exists on the ticket). For v1, dedup relies on the hash-set diff being idempotent across restart.

Hash is stored eagerly in `wlcb002-read-and-diff` (matches PRO-99/PRO-160 best-effort pattern). Trade-off accepted: if Linear API fails after the eager store, the row is not retried (failed silently). This matches PRO-99's design.

### Re-dispatch

Same ticket dispatched twice → two separate completion log rows (different timestamps → different hashes → different comments). Correct behavior — each dispatch produces its own report.

### Completion log replay (static data wipe)

State-wipe init pattern: if `lc_pinged_hashes` is empty and file has rows, seed all hashes silently. No historical comments posted.

## Failure Modes

### Linear API down

**Component 1:** `continueOnFail: true` on `w4042`. Dispatch succeeds; only the state move fails. Bridge will eventually move ticket when the worker completes.

**Component 2:** `wlcb009-post-comment` and `wlcb010-move-in-review` have `retryOnFail: true, maxTries: 3, waitBetweenTries: 3000`. After exhaustion, hash is already stored (eager pattern). Known limitation documented in WORKFLOW_MAP.md.

### Completion log file missing (ENOENT)

Same as PRO-99: if `lc_pinged_hashes` is non-empty and file is ENOENT, fire regression alert via Telegram. Halt Linear posting until recovery.

### Malformed completion row

`try { JSON.parse(row) }` — skip malformed rows. Hash still stored (prevent infinite retry loop). Skip reason recorded.

### Double dispatch click

Listener returns 409 (receipt already exists). W4 shows "Already dispatched." Component 1 only fires on the 202 branch → no double state move.

## PRO-99 / PRO-160 Interaction

**No conflict.** The two watchers are fully independent:

1. **Separate static data** — different workflow IDs → different `$getWorkflowStaticData('global')` namespaces (`cc_completion_pinged_hashes` vs `lc_pinged_hashes`).
2. **Read-only file access** — both only `readFileSync`. Append-only invariant unbroken.
3. **Independent hash sets** — a row processed by one watcher doesn't affect the other.
4. **Same seed/regression behavior** — both protect against historical storms and file regression independently.

The PRO-160 SHA-1 hash-set diff algorithm is battle-tested (shipped 2026-04-28, 8-case test suite). The bridge reuses it verbatim with different static data keys.
